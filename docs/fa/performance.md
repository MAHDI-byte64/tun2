## روی localhost

کاربر ← ورودی ← خروجی ← سرور echo، ۲۵۶ MiB برگشت داده شده، هر دو سمت و سرور echo روی یک ماشین مجازی Xeon چهارهسته‌ای (۲٫۱ GHz). همه CPU را با هم تقسیم می‌کنند، پس این مقایسهٔ تنظیم‌هاست. لینک واقعی بین دو سرور معمولاً اول از شبکه محدود می‌شود.

| تنظیم | Mbit/s در هر جهت |
|---|---|
| `tcp`، بدون رمزنگاری | 5,200-6,600 |
| `tcp`، AES-256-GCM | 3,800-4,000 |
| `tcp`، ChaCha20-Poly1305 | 2,100-2,800 |
| `tcpmux`، AES-256-GCM | 3,200-3,300 |
| `ws` + mux، AES-256-GCM | 2,800-3,100 |
| `wss` + mux، AES-256-GCM + TLS | 2,300-2,500 |

روی یک runner از GitHub Actions (۲ vCPU): ‏`tcpmux` ‏2,960-3,420، `quic` ‏810-950، `kcp` ‏600-670 Mbit/s. QUIC و KCP هر بسته را در فضای کاربر پردازش می‌کنند.

UDP از میان `tcpmux` (۸ client، هرکدام ۳۲ بسته در راه): حدود ۱۴۰٬۰۰۰ بسته در ثانیه در هر جهت. یک تانل بی‌کار حدود ۹۰ µs به رفت‌وبرگشت UDP اضافه می‌کند.

حافظه (RSS، ساخت ریلیز ایستای musl با mimalloc): حدود ۸ MiB برای هر سمت در حالت بی‌کار روی `tcpmux`. ۱۰۰ اتصال کاربر بی‌کار روی mux حدود ۱ MiB اضافه می‌کنند؛ ۱٬۰۰۰ جریان UDP بی‌کار حدود ۵ تا ۹ MiB. بدون mimalloc (پایین را ببینید) یک سمت بی‌کار حدود ۶ MiB می‌گیرد.

### allocator

ساخت‌های ریلیز از [mimalloc](https://github.com/microsoft/mimalloc) به‌عنوان allocator سراسری استفاده می‌کنند: allocator خودِ musl برای اندازه ساخته شده، نه سرعت، و مسیر بسته زیاد allocate می‌کند. روی runnerهای GitHub Actions (۲ vCPU)، ساخت‌های ایستای musl، با و بدون آن، ۲۸ تنظیم از بنچمارک توان عبوری، هرکدام ۳ دور متناوب اندازه گرفته شد:

| | mimalloc | allocator خود musl |
|---|---|---|
| توان عبوری، میانگین روی ۲۸ تنظیم | **+۳۴٪** | |
| توان عبوری با mux، `wss`، `quic`، `kcp` | ‏+۲۵ تا +۱۰۰٪ | |
| توان عبوری `tcp` ساده و `ws` بدون mux | در ۱۲٪ به هر طرف | |
| حافظه، بی‌کار | 8.1 MiB | 6.0 MiB |
| حافظه، ۱۰۰ اتصال بی‌کار | +1 MiB | ‏+1.7 تا +5 MiB (متغیر) |
| حافظه، ۱٬۰۰۰ جریان UDP بی‌کار | ‏+6 تا +9 MiB | +4 MiB |

mimalloc به‌طور پیش‌فرض اولین arena خودش را زود commit می‌کند، که یک سمت بی‌کار را به ۱۵٫۶ MiB می‌رساند؛ کاریز آن را در شروع خاموش می‌کند (`MIMALLOC_ARENA_EAGER_COMMIT=0`، در `src/allocator.rs` گذاشته می‌شود مگر اینکه محیط آن را تنظیم کرده باشد)، و ۸٫۱ MiB از همین‌جا می‌آید.

برای کمترین حافظه، بدون آن بسازید:

```bash
cargo build --release --no-default-features --features quic,kcp
```

## روی مسیر پراتلاف

تست‌ها یک شبیه‌ساز لینک دارند: تأخیر، اتلاف تصادفی یا انفجاری و یک گلوگاه ۵۰ Mbit/s با صف ۵۰ms. سمت TCP آن TCP فرستنده را مدل می‌کند، پس اتلاف `tcpmux` را مثل یک مسیر واقعی کند می‌کند. با رفت‌وبرگشت ۶۰ms و اتلاف در هر دو جهت:

| ترنسپورت | دانلود با اتلاف ۰ / ۱ / ۵٪ |
|---|---|
| `tcpmux` | 48.1 / 2.3 / 0.9 Mbit/s |
| `quic` (Cubic) | 47.9 / 2.7 / 1.0 Mbit/s |
| `quic` (BBR) | 47.5 / 47.4 / 45.7 Mbit/s |
| `kcp` | 31.4 / 28.5 / 22.5 Mbit/s |
| `kcp`، FEC 10 / 3 | 25.4 / 26.1 / 26.6 Mbit/s |

- **کنترل ازدحامِ مبتنی بر اتلاف زیر اتلاف تصادفی فرو می‌ریزد**، هم TCP و هم QUIC Cubic. `quic` با BBR و `kcp` سرعتشان را نگه می‌دارند.
- **BBR صف مسیر را پر می‌کند.** در یک دانلود، حدود نیمی از بسته‌های UDP که با آن یک اتصال را تقسیم می‌کردند گم شدند، پس Cubic پیش‌فرض می‌ماند.
- **پنجرهٔ پیش‌فرض KCP (۱۰۲۴ بسته) مسیرهای کوچک را بیش از حد پر می‌کند.** پنجره‌ای نزدیک پهنای‌باند × RTT / 1300 بسته صف کمتری می‌سازد، ولی زیر اتلاف سرعت کمتری نگه می‌دارد.

## تنظیم برای سرعت

۱. **ترنسپورت را متناسب با مسیر انتخاب کنید:** روی مسیر تمیز `tcp` / `tcpmux`، روی مسیر پراتلاف `kcp` یا `quic` با BBR ([ترنسپورت‌ها](transports.md)).
۲. **از `profile = "ultraspeed"` استفاده کنید،** یا `tunnel.mux.stream_window` را بالا ببرید. یک stream در هر رفت‌وبرگشت حداکثر یک پنجره جابه‌جا می‌کند، پس یک stream تقریباً به پهنای‌باند × RTT نیاز دارد (۱۰۰ Mbit/s با ۱۰۰ms: ‏۱٫۲۵ MB).
۳. **`encryption = "auto"` را نگه دارید.** روی CPUهای دارای دستور AES، AES-256-GCM را برمی‌دارد که آنجا سریع‌ترین رمز است. `none` باز هم سریع‌تر است ولی فقط احراز هویت می‌کند.
۴. **برای کاربرهای موازی زیاد اتصال اضافه کنید:** `tunnel.mux.connections` streamها را روی اتصال‌های TCP بیشتر پخش می‌کند، هرکدام با پنجرهٔ ازدحام خودش.
۵. **برای اتصال‌های زیاد** سقف فایل‌های باز را بالا ببرید (unit سیستم‌دی `LimitNOFILE=1048576` می‌گذارد).


## 2.10.0 قبل و بعد

ماتریس زیر 2.9.3 (`before`) در برابر 2.10.0 (`after`) است روی همان کانتینر ۴ هسته‌ای، روی مسیرهای شبیه‌سازی‌شدهٔ `tests/link`؛ پس اعداد دو بیلد را با هم مقایسه می‌کنند، نه یک خط واقعی را: یک جریان دانلود، هشت جریان، و یک جریان UDP با بسته‌های ۱۲۰۰ بایتی با نرخ ۴۰۰۰ در ثانیه (۳۸ مگابیت بر ثانیه) با صدک‌های تأخیر و سهم رسیده. هر خانه ده ثانیه از یک اجرای تنهاست.

چطور بخوانیم. در ردیف‌های localhost تفاوت‌های زیر حدود ۱۰٪ نویز است. ردیف‌های `wan40` و `rate50` به پنجرهٔ پروفایل، رفت‌وبرگشت و سقف ۵۰ مگابیت محدودند، پس ستون‌های جریان‌شان نمی‌توانند زیاد تکان بخورند؛ آنچه آنجا تکان می‌خورد تأخیر UDP است. در ردیف‌های `wan40-loss1` و `wan100-jitter` برای `tcpmux`، `wss` و `quic`، جریان UDP خیلی بیشتر از ظرفیت مسیر است، پس ستون‌های تأخیر و سهم رسیده یک صف سرریزشده را اندازه می‌گیرند و از یک اجرا تا اجرای بعد نصف یا بیشتر، به هر دو سو، جابه‌جا می‌شوند؛ ستون‌های جریان‌شان هم به جای افتادن اتلاف‌های تصادفی بسته است و همین‌قدر نوسان دارد. فقط KCP که به جای صف کردن دور می‌ریزد و اتلاف را با FEC بازمی‌سازد، روی آن مسیرها عدد پایدار می‌دهد، و همان ترنسپورتی است که باید روی آن‌ها به کار برود.

آنچه در 2.10.0 عوض شده، دسته‌ای شدن دیتاگرام‌ها در مسیرهای UDP و KCP، حذف کپی‌های سر راه، دنبال کردن مسیر توسط پنجرهٔ ارسال KCP (هیچ‌وقت کمتر از پنجرهٔ پروفایل)، و پنجرهٔ ارسال بزرگ‌تر QUIC در پروفایل ultraspeed است. جایی خودش را نشان می‌دهد که CPU یا پنجره حد بود: ردیف‌های localhost با یک جریان تا ۴۵٪ و با هشت جریان تا دو برابر بالا می‌روند (KCP balanced از ۱۲۷۶ به ۲۴۹۴ مگابیت، QUIC gaming از ۱۳۳۹ به ۲۶۲۷)، p99 تأخیر UDP در ردیف‌های `wan40` برای ترنسپورت‌های TCP‌پایه و QUIC بین ۱۰ تا ۳۵٪ پایین می‌آید، KCP ultraspeed با هشت جریان روی مسیر ۴۰ میلی‌ثانیه و مسیر پرلرزش ۱۰ تا ۱۶٪ می‌گیرد و p99 آن روی مسیر پرلرزش نصف می‌شود (۲۱۹ به ۱۱۰ میلی‌ثانیه)، و QUIC ultraspeed با هشت جریان روی مسیر ۴۰ میلی‌ثانیه از پنجره‌اش ۵۵٪ می‌گیرد. ردیف‌های تک‌جریان WAN همان‌جا می‌مانند که پنجره‌شان می‌گذارد.

## اجرای بنچمارک‌ها

```bash
scripts/bench.sh run before                                                # the matrix
cargo test --release --test tunnel throughput -- --ignored --nocapture     # localhost
cargo test --release --test tunnel udp_ -- --ignored --nocapture           # UDP rates
cargo test --release --test tunnel lossy_link -- --ignored --nocapture     # lossy path
cargo test --release --test tunnel game_traffic -- --ignored --nocapture   # games, ~45 min
scripts/rss.sh tcpmux 100                                                  # memory
```

`KARIZ_BENCH_ONLY=kcp` بنچمارک‌های `lossy_link` و `game_traffic` را به ردیف‌هایی محدود می‌کند که نامشان `kcp` دارد. `KARIZ_BENCH_LOSS=1` یک نرخ اتلاف را اجرا می‌کند.

**ماتریس** (`bench_matrix`، که `scripts/bench.sh` اجرایش می‌کند) همان چیزی است که دو بیلد را با آن مقایسه می‌کنیم: چهار ترنسپورت (`tcpmux`، `wss`، `kcp`، `quic`) × سه پروفایل × پنج مسیر (localhost؛ RTT ۴۰ میلی‌ثانیه؛ ۴۰ میلی‌ثانیه با ۱٪ اتلاف؛ ۱۰۰ میلی‌ثانیه با ۲ میلی‌ثانیه جیتر و ۰٫۳٪ اتلاف؛ ۴۰ میلی‌ثانیه با ۵۰ مگابیت بر ثانیه و صف ۵۰ میلی‌ثانیه)، هر کدام با یک دانلود تک‌جریانه، یک دانلود هشت‌جریانه و یک جریان UDP از بسته‌های ۱۲۰۰ بایتی با نرخ ۴۰۰۰ در ثانیه (اکو می‌شوند، پس جدول رفت‌وبرگشت و درصد تحویل را هم دارد). `scripts/bench.sh run <label>` جدول را در `target/bench/<label>.md` می‌نویسد و `scripts/bench.sh compare before after` دو جدول را کنار هم با درصد تغییر چاپ می‌کند. `KARIZ_BENCH_ONLY=kcp,quic` فقط ردیف‌هایی را نگه می‌دارد که نامشان یکی از بخش‌ها را دارد (`KARIZ_BENCH_ONLY="=kcp balanced local"` یک ردیف دقیق)، و `KARIZ_BENCH_SECS=5` هر اندازه‌گیری را کوتاه می‌کند (پیش‌فرض ۱۰ ثانیه؛ کل ماتریس با ۱۰ ثانیه حدود ۴۰ دقیقه طول می‌کشد). مسیرها شبیه‌ساز فضای کاربر در `tests/link` هستند، پس این اعداد دو بیلد را روی یک ماشین مقایسه می‌کنند و مسیر واقعی را پیش‌بینی نمی‌کنند.
